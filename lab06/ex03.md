# Ex.4 - Access control matrix vs. Linux ACLs

**Core idea:** the access control matrix (Harrison-Ruzzo-Ullman model) has a row per subject, a column per object, and a cell P[s,o] holding a set of rights. Linux ACLs store the matrix **by column**: each object (inode) keeps the list of (subject, rights) entries for itself. Capabilities would be the row-wise storage.

| Model concept | Definition in the model | Linux / ACL equivalent |
|---|---|---|
| **User** | A principal (person) on whose behalf subjects act | An account identified by UID, plus its groups (GID). Example: `alice`, group `IS-Lab` |
| **Subject** | Active entity that performs operations; a row of the matrix | A **process**, running with an effective UID/GID and supplementary groups. Example: a shell started by alice |
| **Object** | Passive entity that is accessed; a column of the matrix. In the model S ⊆ O, so subjects are also objects | Files, directories, devices, sockets (inodes). Processes are objects too, for example the target of `kill` |
| **Right** | An element of the finite set R, such as read, write, execute, own | `r`, `w`, `x` (plus ownership of the inode). Cell P[alice, file] corresponds to the ACL entry `user:alice:rw-` |
| **Atomic operation** | The six primitives: *enter r into P[s,o]*, *delete r from P[s,o]*, *create subject*, *create object*, *destroy subject*, *destroy object* | enter/delete: `setfacl -m` / `setfacl -x` (and `chmod`). create object: `touch`, `mkdir`. destroy object: `rm`. create subject: `fork` / `useradd`. destroy subject: `kill` / `userdel` |
| **Command** | A named sequence of atomic operations, executed only if its conditions hold (for example `if own ∈ P[s,o]`) | `setfacl -m u:bob:r file` is the command *confer_read*. The kernel checks the condition: only the owner (or root) may change the ACL. A script such as `ex02.sh` is a sequence of commands |
| **State** | The triple Q = (S, O, P): the current subjects, objects and matrix | All current processes/users, all inodes, and the permission data stored in them (mode bits plus ACL xattrs). Visible with `getfacl -R` or `ls -l` |
| **State transition** | Q ⊢ Q' : a command moves the system to a new state by changing S, O or P | Running `setfacl`, `chmod`, `chgrp` or `touch` changes the stored ACLs (see the example below) |
| **Leak of rights** | A command *leaks* r if it enters r into a cell P[s,o] that did not have it. Whether a right can leak from a given state is the *safety problem*, undecidable in general | See below |

## Example of a state transition

```
Q  : getfacl file  ->  user::rw-   group::r--   other::r--
cmd: setfacl -m u:bob:rw file          # enter(rw, bob, file)
Q' : getfacl file  ->  user::rw-   user:bob:rw-   group::r--   mask::rw-   other::r--
```

Only one cell of the matrix changed: P[bob, file] went from ∅ to {r, w}.

## Leak of rights in Linux

- **By design (DAC):** the owner can run `setfacl -m u:bob:r secret` and give a right to anyone. The model cannot prevent this.
- **By inheritance:** with `chmod 2770 /home/IS-Lab` (setgid), every new file automatically gets group IS-Lab. Rights on future files are therefore given to all group members without the creator doing anything. The explicit form is a default ACL: `setfacl -d -m g:IS-Lab:rwx /home/IS-Lab`.
- **Beyond the matrix:** a subject holding `r` can copy the contents into its own file and become the owner of the copy. Discretionary control cannot stop this (the confinement problem).
- **Setuid programs and root:** both bypass or extend the rights listed in the matrix.
